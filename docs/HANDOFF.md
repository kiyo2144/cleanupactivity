# ひろまち 開発引き継ぎ資料

## 1. この資料について

本資料は、地域清掃活動記録アプリ「ひろまち」の企画・開発内容を Codex に引き継ぐためのものです。

- ここに記載する機能は、明記がない限り**計画中であり、実装済みではありません**。
- 「決定済み」「構成案」「将来機能」「未決定」を区別して扱ってください。
- 既存コードやデータベースの有無、実装進捗は、実際のプロジェクトファイルを確認するまで推測しないでください。

## 2. プロダクト概要

- 名称: ひろまち
- 種別: 地域のゴミ拾い・清掃活動を記録し、住民同士で共有する Web アプリ
- 主な対象: 地域住民全般。特に、徒歩や自転車で町内を移動し、日常の中でゴミを見つけたり清掃活動に参加したりする人
- 解決したい課題:
  - ゴミのポイ捨てが多く、地域の景観維持が難しい
  - 個人の清掃活動が周囲から見えにくく、達成感や継続のきっかけを得にくい
  - 地域住民同士の清掃活動への参加・協力につながりにくい
- 目指す状態: 現実のゴミ拾いを無理なく習慣化し、活動記録の共有を通じて地域の協力を促す

アプリ内の記録や競争そのものを目的にせず、**現実の清掃活動を増やし、続けやすくすること**を優先します。

## 3. 決定済みの仕様

### 基本方針

- 活動中に逐一操作するのではなく、**清掃活動が終わった後に内容をまとめて記録**する。
- 写真の登録は**任意**とする。
- ゴミを拾うたびに撮影する方式や、活動中の動画撮影は採用しない。
  - 撮影の手間によって清掃活動の手軽さが失われるため
  - 動画はファイルサイズが大きく、撮影者も必要になるため
- 自分の活動だけでなく、他の利用者の活動も閲覧できるようにする。
- 成果を見える形にして達成感と継続意欲につなげるが、虚偽記録を過度に誘発する設計は避ける。

### 活動記録で扱う情報

次の項目を基本とします。詳細な入力形式や必須・任意の区分は、写真以外はまだ最終確定していません。

- 活動日
- 活動場所
- 活動時間または所要時間
- 拾ったゴミの量や種類など、成果を表す情報
- コメント・感想
- 写真（任意）

## 4. MVP（最小構成）

Day8 に見せる中核機能は次の3つです。

1. **ユーザー登録・ログイン**
   - 利用者がアカウントを作成し、ログインできる。
2. **清掃活動の記録**
   - 活動後に、清掃内容をまとめて登録できる。
3. **活動記録の閲覧**
   - 自分および他の利用者の活動記録を閲覧できる。

MVPでは、まずこの3機能が一連の流れとして動くことを優先します。将来機能を先に作り込まないでください。

## 5. 画面構成案（5画面）

以下は実装のたたき台となる**構成案**です。画面名、画面分割、遷移の詳細は未確定です。

### 1. ユーザー登録・ログイン画面

- 新規ユーザー登録
- ログイン
- ログアウトへの導線

### 2. ホーム／みんなの活動一覧画面

- 他の利用者を含む活動記録の一覧
- 活動日、利用者、場所、成果、任意写真などの概要表示
- 活動詳細と新規記録画面への導線

### 3. 活動記録作成画面

- 清掃活動後のまとめ入力
- 活動日、場所、活動時間、成果、コメントなどの登録
- 写真の任意添付
- 入力内容の検証と保存

### 4. 活動記録詳細画面

- 1件の活動記録の詳細表示
- 投稿者、活動内容、成果、コメント、任意写真の表示
- 編集・削除機能を設ける場合は、本人の記録だけに制限する

### 5. マイページ画面

- 自分のプロフィール
- 自分の活動記録一覧
- 自分の累計活動回数など、MVPで無理なく算出できる成果の表示候補

想定する基本導線は「登録／ログイン → 活動一覧 → 活動を実施 → 活動後に記録 → 一覧・詳細・マイページで成果を確認」です。

## 6. システム構成と開発技術

### 確定技術

- Webアプリケーションフレームワーク: **Flask**
- ORM: **Peewee**

以前に別の技術案があった場合でも、上記を現時点の確定事項として優先します。

### 候補技術・未確定技術

以下は採用候補であり、**決定済みではありません**。既存プロジェクトを確認し、必要に応じて選定してください。

- データベース: SQLite（開発・小規模運用の候補）
- HTMLテンプレート: Jinja
- 画面スタイル: CSS、Bootstrapなど
- 認証・セッション管理: Flask-Loginなど
- パスワードのハッシュ化手段: Werkzeugなど
- フォーム処理・CSRF対策: Flask-WTFなど
- 画像保存先: ローカル保存または外部ストレージ
- 本番サーバー、ホスティング先、デプロイ方法
- テストフレームワークとCI

候補技術を、確認なしに確定仕様として扱わないでください。

## 7. データ設計のたたき台

以下はMVPに必要と考えられる最小モデルの案であり、実装済みではありません。

### User（利用者）

- id
- 表示名
- ログイン用識別子（メールアドレスまたはユーザー名。未決定）
- パスワードハッシュ
- 作成日時

### Activity（清掃活動記録）

- id
- user（Userへの参照）
- 活動日
- 活動場所
- 活動時間または所要時間
- ゴミの量・種類などの成果情報
- コメント
- 写真情報（任意）
- 作成日時
- 更新日時

入力項目、型、必須条件、削除方式などは、画面設計と合わせて確定する必要があります。

## 8. 将来機能

MVP完成後、必要性と工数を確認して追加を検討します。

- 清掃したルートの記録・地図表示
- 活動回数、活動時間、回収量などの集計・可視化
- ランキングや順位表示
- バッジ、連続記録など、習慣化を支援する仕組み
- 地域全体の成果表示
- 他ユーザーへのリアクションや協力を促す機能
- 地域イベントや合同清掃の募集・参加機能
- 通知機能

ランキングは参加意欲を高める可能性がある一方、過度な競争や虚偽記録を招く可能性があります。導入時は、回数だけを競わせないことや、参加への感謝を中心に見せることを検討してください。

## 9. 推奨する実装順

1. 既存ファイルと現在の実装状況を確認する
2. MVPの入力項目、必須条件、画面遷移を確定する
3. Flaskの基本構成と設定方法を決める
4. PeeweeのUser・Activityモデルとデータベース初期化方法を作る
5. ユーザー登録・ログイン・ログアウトを実装する
6. 活動記録の新規登録を実装する
7. みんなの活動一覧と活動詳細を実装する
8. マイページと自分の活動一覧を実装する
9. 必要であれば本人限定の編集・削除を実装する
10. 入力検証、認可、CSRF対策、画像アップロード制限を整える
11. 主要な利用フローをテストする
12. UIを調整し、実際の利用者に試してもらう
13. フィードバックを反映した後に将来機能を検討する

## 12. 実装・設計上の注意点

- **実装済みと推測しない:** ファイルや動作を確認できない機能は、未実装または要確認として扱う。
- **活動中の負担を増やさない:** 入力や写真撮影を強制せず、活動後に短時間で記録を終えられるようにする。
- **写真は任意:** 写真がなくても記録を保存・共有できる設計にする。
- **認可を徹底する:** 編集・削除を実装する場合、本人以外が操作できないようにする。
- **個人情報と位置情報に配慮する:** 自宅付近や人物が写った写真、詳細な移動ルートの公開リスクを考慮する。
- **アップロードを安全にする:** 拡張子だけに頼らない形式確認、ファイル名の無害化、容量制限、保存場所の分離を行う。
- **パスワードを平文保存しない:** 適切にハッシュ化する。
- **表示内容をエスケープする:** コメントや表示名など、利用者入力によるXSSを防ぐ。
- **成果指標を慎重に設計する:** 数字の大きさだけではなく、参加・継続・地域協力を評価できる見せ方を優先する。
- **スマートフォン利用を優先する:** 屋外活動後に使うことを想定し、少ない操作と読みやすい表示を目指す。
- **MVPの範囲を守る:** ルート、ランキング、通知などは、3つの中核機能が完成してから検討する。

## 13. 完了条件（MVP）

少なくとも次の流れを利用者が問題なく実行できる状態を、MVPの完了目安とします。

1. 新規登録してログインできる
2. 現実の清掃活動後に、写真なしでも活動記録を登録できる
3. 登録した記録が保存される
4. 自分と他の利用者の活動記録を一覧・詳細で閲覧できる
5. 自分の活動をマイページで確認できる
6. 他人の記録を不正に変更できない
7. 基本的な入力エラーが適切に案内される
