# ひろまち コーディング規約

## 1. 適用範囲

この規約は、「ひろまち」のPython、HTML、CSS、設定、テストを変更するすべての作業に適用します。変更前に`docs/ai_context.md`と関連設計書を確認してください。

## 2. 技術と依存関係

- Python 3.13、Flask、Peewee、SQLiteを使用し、別のフレームワークやORMへ置き換えない。
- 依存関係は`pyproject.toml`を正とし、検証済みバージョンは`requirements-lock.txt`へ記録する。
- 新規パッケージは、Python標準機能と既存依存で安全かつ簡潔に実現できない場合だけ追加する。
- パッケージ追加時は目的、必須・任意の区分、Python 3.13対応を確認し、READMEとロックファイルも更新する。
- 任意機能用パッケージを、その機能の実装前に必須依存へ追加しない。

## 3. アプリ構成

- アプリの入口は`hiromachi.create_app(config_override=None)`とする。
- Flask拡張機能はモジュール読込時にアプリへ結合せず、`init_app()`で初期化する。
- Flaskアプリ、DB接続、実ファイルをimport時に作成しない。
- Blueprintは`main`、`auth`、`activities`、`users`を維持する。
- URL、HTTPメソッド、エンドポイント名、テンプレート名は`docs/routes.md`と一致させる。
- ルートはHTTP処理、フォームは入力検証、モデルはデータ構造を担当し、役割を混在させない。
- 現在の規模では5モデルを`models.py`に置き、必要になるまで細分化しない。

## 4. Pythonの書き方

- 公開関数と判断が難しい関数には、目的が分かる型ヒントと短いdocstringを付ける。
- 関数と変数は`snake_case`、クラスは`PascalCase`、定数は`UPPER_SNAKE_CASE`とする。
- 関数を小さく保ち、同じ処理を複数ルートへ複製しない。
- 利用者向けメッセージは日本語で統一する。
- 広すぎる例外捕捉で障害を隠さず、想定できる例外だけを処理する。
- パスは文字列連結ではなく`pathlib.Path`で扱う。

## 5. HTTPと画面遷移

- GETは画面表示とデータ取得だけに使用し、DB、セッション、ファイルを変更しない。
- ユーザー登録、ログイン、活動作成、ログアウトなどの状態変更はPOSTで行う。
- POST成功後は303 See OtherでGET画面へリダイレクトする。
- 入力エラーはデータを変更せず、HTTP 200で入力内容とエラーを同じフォームに再表示する。
- 存在しない活動やページ番号は404として扱う。
- 登録・ログイン画面へログイン済みでアクセスした場合は活動一覧へ移動する。
- 初版ではログイン後の任意URLへの`next`リダイレクトを実装しない。

## 6. 認証とセキュリティ

- 認証必須ルートには`login_required`を付け、画面表示だけでなくサーバー側で制御する。
- すべての状態変更フォームをFlask-WTFでCSRF保護する。
- パスワードはWerkzeugでハッシュ化し、平文、復号可能な形式、確認用パスワードを保存しない。
- パスワード、パスワードハッシュ、秘密鍵、CSRFトークン、セッション内容をログへ出さない。
- ログイン失敗時は、ログインIDとパスワードのどちらが誤りか区別しない。
- Jinjaの自動エスケープを無効にせず、利用者入力へ安易に`safe`を付けない。
- 秘密鍵をコードへ直接記述せず、本番では環境変数`SECRET_KEY`を必須とする。
- 本番HTTPSでは`SESSION_COOKIE_SECURE=True`、常に`HTTPOnly`と`SameSite=Lax`を使用する。
- 例外画面へSQL、内部パス、スタックトレース、秘密情報を表示しない。

## 7. フォームと入力検証

- ブラウザー側の`required`、`maxlength`、`min`、`max`だけに頼らず、サーバー側で再検証する。
- 文字列は仕様に従って前後空白を処理し、空白だけの必須入力を受け付けない。
- フォーム検証とDB制約の両方を使用し、DBの`IntegrityError`も処理する。
- 活動日は日本時間の当日以前、所要時間は1～1440分、袋数は0～99とする。
- ゴミの種類はマスタに存在する値を1つ以上選択させる。
- コメントは任意とし、未入力はNULLとして扱う。
- 写真は任意の1枚とし、10MB以内のJPEG・PNG・WebP・HEIC・HEIFだけを実内容まで検証する。
- HEIC・HEIFは先頭画像だけを使い、透明部分がなければJPEG、あればPNGへ変換する。元データを永続保存しない。

## 8. PeeweeとSQLite

- `DatabaseProxy`を通して実行環境ごとのDBを注入する。
- Flaskリクエストの開始時に必要なら接続し、終了時に接続を閉じる。
- SQLite接続で`foreign_keys=1`を有効にする。
- 複数テーブルの更新は`database.atomic()`内で行い、一部だけ保存しない。
- 活動とゴミ種類の関連付けは同じトランザクションで保存する。
- 日時はUTCとして保存し、画面表示時に`Asia/Tokyo`へ変換する。
- 日時の既定値には、保存時に現在日時を返す関数を渡す。
- 一覧の順序は`created_at DESC, id DESC`とし、同時刻でも安定させる。
- 関連データはJOINまたは`prefetch()`でまとめて取得し、N+1クエリを発生させない。
- 集計の`SUM`がNULLの場合は0として表示する。
- `create_tables(safe=True)`をマイグレーションの代わりに使用しない。

## 9. セッション、DB、ファイルの保存先

- SQLiteの既定保存先は`instance/hiromachi.sqlite3`とする。
- CacheLibのセッション保存先は`instance/sessions/`とする。
- 活動写真は公開静的ファイルと分けて`instance/uploads/`へ保存する。
- `.env`、DB、セッション、アップロード実体、テスト生成物をGitへ追加しない。
- テストでは`tmp_path`配下の一時DB、一時セッション、一時アップロード先を使い、開発データへ触れない。
- 写真は容量、実内容、許可形式、拡張子を検証し、ランダムな保存名で再エンコードしてから保存する。
- EXIFの向きを反映し、長辺2000px以内へ縮小し、位置情報を含むメタデータを引き継がない。
- 写真は認証必須ルートから配信し、利用者が送信したファイル名をURLやログへ出さない。

## 10. テンプレートとCSS

- すべての画面で`base.html`を継承し、共通ナビゲーションとメッセージ表示を再利用する。
- 入力欄には可視ラベルを付け、プレースホルダーだけで意味を伝えない。
- エラーは問題のある入力欄の近くへ文章で表示し、色だけに依存しない。
- スマートフォン幅を優先し、横スクロールや操作部品の重なりを発生させない。
- JavaScriptがなくてもMVPの主要操作を完了できる構成を維持する。
- ブラウザー側の写真検証は早い案内のためだけに使い、サーバー側の容量・形式・実内容検証を必ず維持する。
- HEIC・HEIFをブラウザーでプレビューできない場合は投稿を拒否せず、投稿後に変換される旨を案内する。
- ローカル画像のプレビューで作成したObject URLは、選び直し、解除、ページ離脱時に解放する。

## 11. テスト

- 機能変更時は正常系だけでなく、入力エラー、未認証、存在しない対象、不正アクセスを確認する。
- 状態変更ルートでは、CSRFなしのリクエストが拒否されることを確認する。
- DB更新テストでは、成功時の保存内容と失敗時にデータが残らないことを確認する。
- 認証テストでは、パスワードが平文でないこととログアウト後に保護画面へ入れないことを確認する。
- ルート変更時は`flask --app hiromachi routes`で設計との一致を確認する。
- 完了前に`pytest`を実行し、既存テストを削除または弱めて失敗を隠さない。
- カバレッジ率だけを目的にせず、権限とデータ整合性を優先してテストする。

## 12. 対象外機能

次の機能は、`requirements.md`、関連設計書、`tasks.md`が更新されるまで実装しません。

- 複数写真、動画、一覧・マイページのサムネイル
- 活動の編集・削除
- メールアドレス、メール認証、パスワード再設定
- 地図、位置情報、ルート記録
- ランキング、バッジ、連続記録
- コメント、リアクション、フォロー
- イベント、通知、管理者画面、JSON API

## 13. 開発記録の保存先

- `docs/lean_canvas.md`は初期検討時の記録として保持し、今後は更新しない。
- 利用者テストの事実、対応状況、次の作業は`docs/tasks.md`へ記録する。
- 確定した仕様変更は`docs/requirements.md`と関連する画面・ルート・DB設計へ反映する。
- 利用者の個人情報は必要以上に記録せず、対象者名は匿名または関係性だけでもよい。
